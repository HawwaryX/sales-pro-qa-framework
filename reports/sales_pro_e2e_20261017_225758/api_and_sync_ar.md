# API والاتصال والمزامنة

## الحالة الحالية بعد تغير السياسة

المراجعة الفعلية3 تتضمن `sales.infinity-tech.sa`؛ لا حاجة لإعادة السماح أو ترحيل المهمة بسبب غياب القاعدة. بعد هذا التغير نجح فحص HEAD واحد إلى جذر المضيف عبر الوكيل الموروث: CONNECT200 وTLS موثّق وorigin HTTP404، دون redirect. بقي DNS الافتراضي فاشلًا في Linux وAndroid. نجاح HTTP من الجذر لا يثبت URL API كاملًا أو هوية TEST أو نجاح اتصال التطبيق.

الأدلة: [السياسة](evidence/followup_20261018/effective_policy.json)، [إعادة الاختبار الوحيدة](evidence/followup_20261018/backend_targeted_retest.json)، [DNS المضيف](evidence/followup_20261018/host_dns_after_policy_update.json)، [DNS Android](evidence/followup_20261018/android_dns_after_policy_update.json).

## تمييز الأدلة

1. APK: أصل HTTPS `https://sales.infinity-tech.sa` في libapp.so للمعماريات الثلاث. الإزاحات: arm64=850080؛ x86_64=850237؛ armv7=3944892. لا إعداد endpoint صريح في manifest أو ملفات assets/JSON المفحوصة؛ libapp يتضمن أسماء network.dart وbaseUrl.
2. سلاسل المسارات الفعلية تشمل `/api/v1/auth/login` و`/api/v1/auth/years` و`/api/v1/auth/company` و`/api/v1/me` و`/api/v1/customers` و`/api/v1/sync/pull` و`/api/v1/sync/push`. هذه قيم منفصلة؛ لم يُثبت تركيب URL الكامل أو معاملات الطلب، فلا تُختلق endpoints من دمجها.
3. تشغيل فعلي: أثناء تحديث القوائم رُصد طلب DNS إلى المضيف نفسه. [الأثر](evidence/runtime_dns_observed.jsonl). يربط ذلك المضيف بمحاولة التطبيق الفعلية، ولا يثبت وحده نوع الخادم أو إعداد TEST أو طلب API وصل.
4. التخزين المحلي قبل الدخول: جرد أسماء مفاتيح secure storage أظهر حالة الترحيب واللغة، ولم يظهر endpoint عام محفوظ؛ لا فك لتخزين محمي ولا نشر لقيمه. عدم رؤية مفتاح لا ينفي إعدادًا مشفرًا أو محملًا لاحقًا.
5. لم تُرصد استجابة DNS للمضيف في نافذة الالتقاط، وفشل getaddrinfo في المضيف EAI_AGAIN(-3). سجل التطبيق أظهر Failed host lookup للخطوط فقط؛ لا يثبت أن خطأ القوائم له السبب نفسه حصريًا.
6. HEAD تاريخي محفوظ في الالتزام d806c39 من المضيف عبر وكيل الجلسة: **CONNECT403؛ origin HTTP000؛ curl exit56؛ CONNECT tunnel failed, response403**. لم يصل ذلك الفحص إلى الأصل ولم يرسل بيانات حساب. أعادت المحاولة الأحدث بعد تغير السياسة CONNECT200 وHTTP404 للجذر؛404 ليست استجابة API مختبرة.

## معنى CONNECT403 التاريخي

الرفض السابق كان في طبقة الوكيل قبل الوصول إلى خادم الأصل، وليس رفض حساب أو دليل frontend مقابل API. السياسة الحالية restricted/enforced مع observations_current=true وتشمل المضيف؛ حاجز CONNECT403 لم يعد قائمًا في فحص Linux المعتمد. أُجري الاختبار الجديد مرة واحدة بسبب تغير السياسة، دون DNS بديل أو TLS غير موثق أو ربط IP مصطنع.

## المصادقة وهوية TEST

أُرسل نموذج UI بالحساب النهائي المحدد: «اختر الفرع والسنة المالية.» الفرع الوحيد افتراضي والسنة غير متاحة. لا منزل مصادق عليه أو /me أو إثبات هوية حساب. لا يُحكم بخطأ كلمة المرور. ادعى المستخدم أن قاعدة البيانات TEST وأذن ببيانات مالية اختبارية، لكن مطابقة الخادم الفعلي لهذه البيئة لم تثبت؛ لم تُنفذ mutations.

## online ثم offline

| المرحلة | الحالة | الفعلي |
|---|---|---|
| وصول المضيف عبر الوكيل | PASS محدد للفحص الحالي | CONNECT200؛TLS موثّق؛HEAD الجذر HTTP404، دون إثبات API أو TEST |
| وصول التطبيق إلى القوائم online | BLOCKED | DNS Android ما زال يفشل؛ لا استجابة قوائم موثقة |
| إدخال الحساب وتقديم النموذج | نُفذ؛ المصادقة BLOCKED | حاجز الفرع والسنة المحلي |
| أخطاء دون اتصال قبل الدخول | PASS المحدد | رسالة واضحة دون انهيار مرصود |
| إعادة شبكة المحاكي | PASS المحدد | أزيل العزل وعاد الوكيل؛ لا نجاح backend |
| عمليات أعمال online | BLOCKED | لم يفتح نموذج مصادق |
| إنشاء أعمال offline ثم sync | BLOCKED | لم يتحقق online أولًا ولا سجل اختبار |
| منع التكرار/تعارض/refresh token | BLOCKED | لا جلسة أو سجل مزامنة |

## نتيجة استئناف الدفعة d806c39 والتطور اللاحق

في استئناف الدفعة d806c39 بتاريخ18أكتوبر أُعيد تحديث القوائم والحساب المطابق مُعبّأ؛ لم يظهر المركز الرئيسي أو2026. لم تظهر استجابة API في logcat المفلتر أو endpoint كامل جديد في UI. لم تكرر HEAD المحجوبة في تلك الدفعة، ولم تختبر offline مجددًا.

الفقرة السابقة تصف استئناف الدفعة d806c39. منذ ذلك الحين أصبحت القاعدة فعالة في المراجعة3؛ لا تُطلب إعادة إدخالها أو ترحيل المهمة لإضافتها. المتطلب الخارجي الباقي هو مسار Android DNS/proxy/trust مدعوم، أو جهاز اختبار مصرح بشبكة backend عاملة؛ لا مسار مباشر/VPN/TCP معتمد متاح محليًا. [التشخيص الحالي](android_connectivity_ar.md).

بعد وصول مشروع للخادم، تُراجع هوية TEST وتحمّل القوائم ثم يقدم الحساب نفسه بالقيم المحددة وتبدأ الأعمال online. لا يحتاج ذلك إعادة إرسال بيانات الحساب.

## تشخيص Android اللاحق

أُثبت سابقًا HTTPS فعلي داخل Android لوجهة تحكم عبر وكيل الجلسة وCA المناسبة للمسبار: TLS1.3 وHTTP200. تجربة proxy نظامي مؤقت قبل تغير السياسة لم تفتح القوائم، وأعيد الإعداد الأصلي. هذا لا يثبت اتصال التطبيق بعد تحديث السياسة أو يجيز تعطيل تحقق شهاداته. لا مصادقة أو أعمال مثبتة من أدلة الشبكة وحدها؛ الأعداد التنفيذية المحدثة في [الدفتر](test_ledger.json)، مع فصلها عن [تشخيص البيئة](android_connectivity_ar.md).

## متابعة التنفيذ بعد تطبيق المراجعة 3

المراجعة 3 تسمح بالمضيف؛ CONNECT200 وTLS موثق ثم HTTP404 للجذر من Linux. DNS في Android ما زال يفشل بـUnknownHostException؛ القوائم لم تُحمّل ولا دخول مصادق. نجحت RT-33–35 (تكبير الخط وTab ونص 1024 حرفًا دون تقديم)، وحالة تخطي الترحيب BLOCKED في مستخدم مؤقت حُذف بعد العودة للأصلي. الدفتر: PASS: 26؛ FAIL: 4؛ BLOCKED: 55؛ NOT RUN: 2؛ 87 حالة. لا معاملات أو مزامنة أعمال. لا إعادة للطلب المحجوب أو الفحص الثابت.
